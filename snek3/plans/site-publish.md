# The chart viewer keeps itself current

**Status: proposed 2026-09-05, for discussion.** The question: can both boxes publish their charts as each
wave finishes, so the [Pages viewer](https://twang35.github.io/Snek/) is current without a progress update,
and without bringing back the merge failures the box's `snek3/runs/` collisions caused?

## What exists already

| piece | today |
|---|---|
| the site | `docs/` on `master`, generated by `tools/publish_pages.py` from `viewer/` and `runs/`: `index.html`, `manifest.js` (276 KB, one record per arm reduced from the JSONs), `charts/*.png` (51 MB) |
| who commits it | the progress-update skill, by hand, on the laptop |
| the desktop's finished work | **already published**: the daemon pushes every finished job's `.md`, `.png`, `_evals.json` and stage-B files to `results/<job-id>/` on the `results` branch when the scheduler reports it done. The progress update imports from there |
| the laptop's finished work | nowhere but the laptop's own `runs/`, until a progress update commits it |
| the two boxes' live state | `ops-status` (desktop) and `laptop-status` (laptop), one writer each, `--force-with-lease`, worktrees outside the checkouts |

So "publish charts as each wave completes" is **done on the desktop and missing on the laptop**, and nothing
builds the site from the feeds except a person.

## Why the old merge failures happened, and what avoids them

The box fast-forwards `master` with `git merge --ff-only`. It refused whenever its working tree held a file
at a path `master` tracked — a chart the box had drawn under `snek3/runs/` that the laptop had also committed.
Two rules remove the failure entirely, and every option below keeps both:

1. **One writer per branch.** `master` is the laptop's (a person's). Every automated writer gets its own branch.
2. **The box's checkout of `master` holds nothing generated at a tracked path.** Since 2026-09-03 the box writes
   to the gitignored `desktop/runs/`, and every automated branch is written through a worktree outside the
   checkout. A site built the same way cannot collide with anything.

A third rule for the new part: **the site branch is a snapshot, not a history.** A build rewrites one commit
and pushes `--force-with-lease`, as the status branches do. A history of 1-2 MB of PNGs per wave would grow
the repository by ~20 MB a day; a snapshot stays the ~51 MB the page needs.

## Options

| | A. the desktop daemon builds the site | B. a GitHub Action builds it | C. the laptop automates today's commit |
|---|---|---|---|
| laptop's finished work | the laptop scheduler publishes each finished wave and pass to a `laptop-results` branch, the mirror of `results` | same | stays in `runs/` |
| the builder | the daemon, on any network cycle where `results` or `laptop-results` moved: stage both feeds plus its own `desktop/runs/`, run `viewer_manifest` + `publish_pages` into a `site` worktree, snapshot-push `site` | an Action on push to either feed: check out `master` for `viewer/` and `tools/`, fetch both feeds, build, push `site` | a launchd job running the progress update's sync + publish and committing `docs/` to `master` |
| Pages source | branch `site`, path `/` | branch `site`, path `/` | `master` `/docs`, as now |
| writers on `master` | none automated | none automated | **the job, from the person's checkout** |
| moving parts | one more daemon job type, one more worktree; reuses `gitbus` | CI outside the repo's toolchain; a 372 MB feed to fetch per run | none new |
| freshness | within a daemon network cycle of a wave closing on either box; the desktop's live charts free, since `desktop/runs/` is local | within a few minutes of a push | whatever the job's interval is |
| the failure it reintroduces | none: rules 1-3 hold | none, but debugging moves to CI | **rule 1 broken**: the job pushes whatever else is committed locally, and stages from a tree the person is editing |

**Recommendation: A.** It is the shape the box already has — the daemon watches branches and publishes
branches — extended by one feed and one output, on the box that is always on. B is defensible and symmetric,
but it fetches a third of a gigabyte to copy a megabyte and moves the one hard-to-debug piece off the machines
we can ssh to. C is what we do by hand today made unattended, and it puts an automated writer on the
person's branch, which is the mistake the whole git bus exists to avoid.

## The plan for A

| step | where | what |
|---|---|---|
| 1 | `tools/scheduler.py` (+ `gitbus`) | **the laptop publishes finished work** the way the daemon does: at a wave's stage B, `hof5000` and `hof30k` ends, copy the wave's `.md`, `.png`, JSON and stage-B files to `laptop-results/<job-id>/` on a `laptop-results` branch through a worktree under `~/.snek3-laptop/results`. Same layout as `results`, so the progress update's importer reads both with one path. The publish is best-effort like `laptop-status`: a failure is logged and the next event retries |
| 2 | `desktop/daemon/` | **the daemon builds the site**: a `site` worktree (`~/snek-bus/site`); on a network cycle where the head of `results` or `laptop-results` changed, stage `desktop/runs/` + every file under both feeds into a build directory, `viewer_manifest.build(build_dir)`, `publish_pages.publish(...)` into the worktree, one commit, `--force-with-lease`. The desktop's `status.json` is local, so pass states on the page are right; the laptop's come from `laptop-status` as they do today |
| 3 | repo settings | Pages source → branch `site`, path `/`. Then `docs/` leaves `master` (`git rm -r docs`; `.gitignore` it) and `publish_pages` writes only to the worktree; a progress update stops committing charts and the manifest to `master` |
| 4 | `tools/progress_update.py` | import closed waves from both feeds; drop the site publish and the chart commit from step 2 of the skill; keep committing a closed batch's JSON to `master` as the archive |
| 5 | later, both feeds | make `results` and `laptop-results` snapshots too, or publish an arm's `_evals.json` once at its cap rather than with every pass: today each pass re-publishes it (1.7 MB x 3 passes x 8 arms per wave), and the `results` pack is 372 MB |

**What stays manual:** the reading. The tables regenerate themselves; the sentences under them are the
progress update, and that is the part worth a person's time.

**What to watch for:** the daemon building while a laptop wave is half-published (the laptop's push is one
commit per job, so a feed is either the old tree or the new one, never half); the site build's cost on the
box (a manifest walk over ~500 arms is seconds; the copy is a megabyte); and `--force-with-lease` losing a
race with itself, which cannot happen with one writer and a single daemon.
